Onboarding

Cyclops, from the top

One eye. Many agents. A single coordinated team. Cyclops coordinates AI coding agents that are already running in your terminal. A background daemon watches your tmux panes, figures out what each agent is doing (working, idle, blocked, waiting on you), delivers messages between agents by literally typing into their panes at safe moments, and writes every fact to a permanent on-disk record. The name is the product's one metaphor: a one-eyed giant — in cyclops watch and cyclops status, the eye glyph (‿ closed, ◑ opening, ◉ open) opens when something needs a human.

Level 1 — The big picture

Three audiences use one system, through the same verbs. You mostly talk to your agents, not to Cyclops: tell an implementer “when you're done, send it to reviewer”, and the agent runs the handoff itself from its own pane.

Underneath, three parties and one direction of trust. Clients talk to the daemon through small socket requests; the daemon is the only thing that talks to tmux for detection and delivery; and everything the daemon learns or does is written to the ledger before it acts. If the daemon crashes, nothing is lost — the facts were already on disk. Click any box below — each one answers the question it usually raises.

cyclops <verb>
the CLI: send, status, list, wait…
A one-shot, synchronous binary. Every invocation opens the socket, sends one JSON request, prints the reply, and exits — it holds no state between calls. Humans, agents, and scripts all use the same verbs; every command takes --json and --plain.
cyclops (bare)
the full-screen workspace
Bare cyclops on a TTY opens a full-screen terminal workspace: project sidebar, tabs, and a live pane canvas fed by its own tmux control-mode connection, with tmux-style Ctrl+B keys, mouse support, and a one-line composer (Ctrl+B s, or the chat button) for messaging agents. It draws the panes itself, but every fact about an agent (name, state, chrome) comes from the daemon — without one, the sidebar says cyclopsd offline.
cyclops watch
the live stream TUI
A long-running dashboard, not a one-shot command. It subscribes to the daemon's live event push and renders every message and state change as it happens — calm admin view by default, firehose one keypress away, the eye in the header. cyclops watch --json is the machine-readable stream. (The old cyclops ui spelling survives only as a deprecated alias.)
cyclops hook
invoked by agents' vendor hooks
Not something you run by hand. The agent CLI (Claude, Codex…) is configured to call this automatically at its own lifecycle events (a turn ending, say). It's fast and silent by design, and always exits 0 so a slow relay never disrupts the agent.

Level 2 — The folder map

The repo splits cleanly into: the product (Rust code in src/), the data the product consumes (resources/ — all TOML and templates, no code), and the things that keep it honest (docs/, demos/, scripts/, tests/). Expand what you're curious about; each crate row also says why it's named the way it is.

src/ 9 the product — 9 Rust crates (a 10th, test-only, lives in tests/)

“Crate” is Rust's word for a package; a repo holding several is a Cargo workspace. The nine product crates live under src/, and the test-only cyclops-testrig lives at tests/testrig — ten workspace members in all. Every crate name is prefixed cyclops- so the published names don't collide with anything else. Expand each one:

cyclops-proto“proto” as in protocol
The shared vocabulary of the whole system: the socket protocol's message types, the ledger schema, the 10-state delivery machine, the agent-state model, scratch paths, and the attention rule (“what needs a human”). Pure data types — no file or network access, and it has never heard of tmux. Every other crate depends on it, so a rule defined here exists exactly once.
cyclops-tmuxthe tmux adapter
The “blast wall”: every tmux invocation in the product lives in this crate, so tmux's quirks are quarantined in one place. Holds the control-mode client (one tmux -C child per watched session), the zero-polling reconciling pane table, version parsing, and the workspace layout engine. One honest exception exists: the daemon runs tmux -V once at boot.
cyclops-ledgerthe append-only record
The mechanics of the on-disk record: append with fsync, recover only a final unacknowledged torn tail after a crash, and keep sequence numbers monotonic across restarts. Lenient replay seals that tail and keeps it when valid; strict workspace replay discards only that tail. What a line means is cyclops-proto's business; this crate only owns how lines get on and off disk. Deliberately no index — a 10,000-line scan measures ~7ms.
cyclops-manifesta manifest declares what a vendor CLI looks like
Parses, validates, and evaluates the TOML manifests that teach Cyclops to recognize an agent CLI (what its pane title or screen shows in each state, which keys decline its modals, how to verify a paste). It compiles the rules and answers “which rule matches?” — it does not decide pane state (fusion in the daemon does) and it never captures screens (the tmux crate does).
cyclops-themecolors
The semantic token vocabulary (role colors, state groups, the eye), theme TOML parsing that tolerates unknown tokens, 256-color fallback, and hot reload implemented as a cheap file-stat check when a repaint is already due — never a watcher thread or a timer. Renderers use tokens, never raw colors, which is why one theme file restyles every surface at once.
cyclops-uithe terminal UI
The live stream TUI behind cyclops watch: calm admin view, firehose one keypress away, the eye in the header, jump-to-pane. Its grid module is the shared rendering vocabulary for state cells, badges, and cause words that the CLI also renders through, so every surface prints things the same way. Its terminal backend is hand-rolled.
cyclops-workspacethe full-screen workspace
What bare cyclops opens on a TTY: a project sidebar, tab bar, and live pane canvas fed by tmux control mode, with tmux-style Ctrl+B keys, mouse support, splits, drag-and-drop, and a one-line composer (Ctrl+B s, or the chat button) that sends @reviewer fix the burst path through the same delivery pipeline. Built on Ratatui/Crossterm with embedded per-pane VT runtimes. It draws the panes itself, but everything it knows about an agent — name, state glyph, chrome — comes from the daemon.
cyclopsdtrailing “d” = Unix daemon convention (like sshd, systemd)
The long-running daemon and the heart of the system: session watching, sensor fusion (deciding each pane's state), the delivery pipeline, fail-closed sender identity, the adoption registry, pane-border chrome, the hooks self-test, and the Unix socket server. Built as a library plus a thin binary so tests can boot the entire daemon in-process.
cyclopsthe product name
The CLI binary. A thin synchronous socket client plus rendering: start, send, status, list, history, thread, wait, name, read, ping, theme, hooks, update, daemon, and workspace save/restore — plus cyclops hook, the receiver vendor hooks invoke. Every command takes --json and --plain. It asks the daemon rather than recomputing any business rule itself; its user-facing sentences live in one file, copy.rs.
cyclops-testriga “rig” for tests — lives at tests/testrig, not src/
Test-only (publish = false). Gives every test its own private, throwaway tmux server so no test can ever touch your real tmux; teardown (including unlinking the socket file) happens automatically when the value is dropped. Guard tests enforce that no other file starts or kills a tmux server.
resources/manifests/how Cyclops recognizes agent CLIs
One TOML file per vendor CLI — four ship: Claude Code (claude), Codex CLI (codex), Antigravity CLI (agy), and Cursor Agent (cursor) — describing what that CLI looks like on screen in each state. Data, not code: teaching Cyclops a new agent CLI is a text edit, no compiler needed. Compiled into the binary with include_str!, seeded into ~/.cyclops/manifests on first run. The seeder never clobbers your edits, but it does refresh files whose bytes it recognizes as its own shipped versions (by hash), so unedited manifests pick up fixes automatically.
resources/themes/17 color themes
dark, light, high-contrast, catppuccin, gruvbox, nord, tokyo-night, plus ten more (ember, sorbet, obsidian, midnight, forest, meadow, seafoam, periwinkle, blossom, buttercream). Every state glyph keeps one fixed meaning under every theme and stays visible under NO_COLOR; a theme switch (cyclops theme <name>) is live at once, including the pane borders.
resources/layouts/workspace presets
solo, duo, quad, ops — each one is the previous preset plus a pane. cyclops start --preset duo --agents claude,codex builds a two-pane implementer/reviewer workspace and starts those CLIs in it (a preset ships names and shapes, never CLIs — the fleet is yours to say). Embedded into the CLI binary with include_str! so a fresh install works with no files.
resources/hooks/vendor hook templates
Templates for each vendor CLI's hook configuration (agy, claude, codex, cursor), rendered by cyclops hooks install <cli> --agent <label> into vendor-isolated paths under ~/.cyclops/hooks/. The command itself refuses to write into ~/.claude, ~/.codex, or any vendor directory — wiring your real setup is deliberate (or delegated to the installer's opt-in --wire-hooks lane).
skills/teaching your agents to use Cyclops
skills/cyclops/SKILL.md is one file that teaches a coding agent the send/wait/reply verbs and the safety rules. During an install, Cyclops's consent-backed --wire-hooks setup may copy it into an existing supported private skill directory only when that exact file is absent. It never creates skill directories or overwrites a current, older, or operator-edited file. You can also copy it manually; every command explains itself with --help, and every delivered message carries its own reply instructions.
docs/guides, reference, and engineering contracts; start at development/HANDOFF.md
Split by audience: docs/development/ holds current engineering contracts, approved charters, and acceptance records; docs/guides/ holds task-focused operating instructions; docs/reference/ holds protocol, manifests, hooks, and measured performance boundaries; docs/public/ powers the rendered public docs site. The developer front door is docs/development/HANDOFF.md. Unusual and important: docs are CI-enforced. Quoted terminal output must match what the binaries actually print (tests/e2e/parity-check.sh) and every quoted file path must exist (scripts/check-doc-paths.py). Treat doc edits like code edits.
demos/runnable proofs
End-to-end scripts that run the real binaries on throwaway tmux servers and touch nothing of yours: daemon status, durable mailbox acceptance without either UI, pane naming, workspace save/destroy/restore, and live theme switching. The maintained messaging journey is m1-send.sh; the complete agent-to-agent claim and reply journey is enforced by tests/e2e/parity-check.sh. House rule: ship a demo with anything a user will do end to end — on this codebase demos have caught defects four times that reading the code did not.
scripts/installer + doc gate
install.sh (the build-from-source installer: builds both binaries, places them on your PATH, backs up your shell profile before touching it, never uses sudo, has --uninstall, and can opt panes into vendor hook wiring), and check-doc-paths.py (the doc-path CI gate).
tests/e2e gates + the test-only tmux rig
tests/e2e/ holds parity-check.sh — the CI gate that re-runs every command shape the README and docs quote against the real binaries (over a hundred checks; more with --with-installer) — plus lib/ (the shared shell rules and the Python probe harness, the one sanctioned poller) and the m1 soak script. tests/testrig/ is the cyclops-testrig crate: the isolated tmux server every tmux-touching test must go through.
website/usecyclops.dev — explicit request only
A SvelteKit landing page, outside the Cargo workspace but checked by its own CI job. Its static/install.sh must match scripts/install.sh byte for byte — CI fails otherwise, and touching either means running parity-check.sh --with-installer. Modify only on explicit request; when you do, run npm run check and npm run build.
root filesREADME, AGENTS, STATUS, findings, CONTRIBUTING…
README.md is the user front door — its quoted terminal output is CI-verified against the real binaries, so never hand-edit an output block. Step 1 of 10 · The commandyou / an agent

In the implementer's tmux pane, someone (a human, or the agent itself — agents run the same CLI) runs the send command. The cyclops binary parses it with clap. Notice that nothing in the command says who is sending — that gets resolved later, on the daemon's side, from evidence.

Where in the code: src/cyclops/src/main.rs · user-facing sentences in src/cyclops/src/copy.rs

Why two binaries — cyclops vs. cyclopsd?

“cyclops” and “cyclopsd” are two separately compiled executables from the same workspace — not two commands inside one program. A “binary” just means a compiled, directly-runnable program file, as opposed to source code or a script an interpreter reads line by line.

cyclops
one-shot: runs, does one thing, exits
invoked directly — by you, or by an agent
cyclopsd
long-running: stays up, holds all the state
you never invoke it — cyclops starts it for you

The split matters for identity: the daemon figures out who's sending by walking the calling process's ancestry up to a watched pane — that trick only works because sending happens from a fresh, separate process each time.

Step 2 of 10 · One JSON line over the socketCLI

The CLI opens the Unix socket at ~/.cyclops/sock, reads the daemon's hello line, and writes a single JSON line: a msg.send request with to, subject, and body. The client is deliberately simple, fully synchronous code — the daemon does all the hard work.

Where in the code: src/cyclops/src/client.rs · types in src/cyclops-proto/src/wire.rs

What does “one JSON line” (NDJSON) actually mean?

NDJSON = newline-delimited JSON: one complete JSON object per line, no wrapping array, no commas between records. Cyclops uses it in two places — this socket exchange is one, the on-disk ledger (a few steps ahead) is the other.

Why it fits a live connection: each line is parseable the instant it arrives — no waiting for a closing ] that a still-open socket may never send.

Step 3 of 10 · Who is actually sending?daemon

The daemon reads the caller's process id from the socket's peer credentials and walks up the process tree until it reaches a process living in a watched tmux pane. The record will say “implementer → reviewer” because that is where the call physically came from — identity is never taken from the request, so nothing in a body can forge the header a recipient reads. No watched pane in the ancestry means the send is refused (fail closed).

Where in the code: src/cyclopsd/src/identity.rs

Step 4 of 10 · Written down before anything happensdaemon

A msg line is appended to the ledger file of every session involved and fsynced to disk before the daemon does anything else. From this moment the message exists durably — a daemon crash can no longer lose it. Its delivery state starts at queued, the first of ten named states every delivery moves through.

Where in the code: src/cyclops-ledger · schema in src/cyclops-proto/src/ledger.rs

On the record: msg line appended to ~/.cyclops/ledger/<session>.ndjson

Show me the actual line that gets written

The exact line this step appends to ~/.cyclops/ledger/main.ndjson:

{"seq":47,"boot_id":"b-a1c2","id":"m-be0129","ts":1735900000000, "kind":"msg","from":"implementer","to":["reviewer"], "subject":"Burst path fix, ready for review","body":"gateway.rs:120. Tests pass.", "deliveries":[{"to":"reviewer","state":"queued","attempts":0,"ts":1735900000000}]}

Same NDJSON idea as the socket protocol, chosen here for a different reason: append-safety. Adding a new fact is just a new line at the end — nothing earlier is touched or re-parsed, which is exactly what a crash-safe record needs. Every later line about this message (a gate decision, a state transition) reuses this same id, so cyclops thread m-be0129 can reconstruct the whole story with one filter.

Step 5 of 10 · Into the queuedaemon

The message is handed to the reviewer pane's delivery worker. Each target pane has exactly one worker and it processes strictly in order (first in, first out), so two messages can never interleave inside one pane's input box. The code reads in call order: msg_send → worker_for → worker_loop → process → gate → attempt_delivery.

Where in the code: src/cyclopsd/src/delivery.rs

What is “a worker”, exactly?
reviewer's worker
one dedicated async task, spawned on first delivery
queue: [msg 2] [msg 3] — strict FIFO
processing msg 1 right now: gate → paste → verify → submit → ACK
msg 2 cannot start until msg 1 fully resolves
implementer's worker
a completely separate task, separate queue
unaffected if reviewer's worker is slow or parked
this is why one broadcast can return mixed receipts
Step 6 of 10 · The gateworker

Before touching the pane, the worker runs eight ordered checks: is the session attached? Is the pane still there, alive, and not in copy-mode? Is a manifest bound? Then it recomputes the pane's fused state with the screen sensor forced, and only idle proceeds. An agent mid-task means hold — and a hold waits on an event (the working-to-idle edge), never on a timer. A modal whose manifest declares decline keys gets auto-dismissed; an agent blocked on quota means park, which is terminal. Every gate decision becomes a ledger line carrying a one-word cause.

Where in the code: src/cyclopsd/src/delivery.rs · spec in docs/development/DELIVERY.md

On the record: one gate line per decision, each with a cause word

Step 7 of 10 · The pasteworker → tmux

The worker re-checks the pane occupant's process id (did the agent restart while we waited? a shell occupant would EXECUTE the text), then pastes the message using tmux load-buffer + paste-buffer, into a buffer named cyc-<daemon pid>-<seq> so concurrent senders can never race on a shared name. The tmux calls go through cyclops-tmux, because that crate owns every tmux invocation in the product — the “blast wall”.

Where in the code: src/cyclops-tmux/src/control.rs

How does tmux itself work — server, session, pane, client?
server
One background process holding everything real: every session, window, pane, PTY, scrollback. Outlives any terminal window; starts on first use, runs until killed.
session
A named group of windows — the thing you attach/detach from. Cyclops watches at this granularity: one control client per session in config.toml's sessions list.
window
One tab within a session, holding one or more panes arranged by splits.
pane
One rectangle running one process tree. This is the unit fusion decides state for, and the unit delivery pastes into.
Clients — anything attached to the server

A client only *looks at* the server; it holds no real state of its own.

• your interactive terminal (renders panes, sends keystrokes)

• the cyclops workspace, rendering the same panes its own way

• cyclopsd's tmux -C control client — no rendering, just a stream of text notifications in, and commands out

This is why several people can attach to one session and see the same panes — and why Cyclops never runs its own PTYs: the tmux server does, Cyclops is just one more client.

Step 8 of 10 · Verify before submitworker

The worker re-reads the pane's input box on a ladder of delays — 0, 120, 240, and 480ms — to confirm the message id is really sitting there. A paste can silently fail; Cyclops never assumes it worked.

Where in the code: src/cyclopsd/src/delivery.rs (VERIFY_DELAYS_MS)

Step 9 of 10 · Submitworker → tmux

One more occupant-pid check, then the manifest's submit key is sent. The reviewer's agent starts its turn with your message as the prompt: a structured header with the sender's verified identity, the subject, the body, and a reply hint at the bottom.

Where in the code: src/cyclopsd/src/delivery.rs

On the record: state transition logged (submitted)

Step 10 of 10 · The receipthook → daemon

When the recipient agent's vendor hook fires, it runs cyclops hook, which posts a report carrying the message id back to the daemon. That marks the record delivered · verified — the agent itself confirmed this exact message. Without hooks wired, Cyclops falls back to screen evidence and honestly records delivered · unverified (screen); a late hook report can still upgrade it — the only legal transition out of a delivered state. The sender's CLI prints one receipt per recipient (a busy pane honestly reads queued · 1 ahead), and every transition along the way is already on disk.

Where in the code: src/cyclops/src/hook.rs · src/cyclopsd/src/ack.rs

On the record: delivered_verified (hook) or delivered_unverified (screen)

Manifests vs. hooks — what's shipped vs. what gets wired
resources/manifests/*.tomlShipped by Cyclops — you don't write these

The “peeking” rulebook: regex over pane title and screen text, per vendor CLI, empirically measured. Seeded into ~/.cyclops/manifests on first run; your edits are never clobbered, and unedited shipped copies are refreshed in place when a fix ships. Detection works with zero setup — but it can only ever produce screen-tier evidence.

vendor hooks → cyclops hookWired once per agent, deliberately

The “walkie-talkie” that upgrades receipts to delivered · verified. Two lanes: cyclops hooks install <cli> --agent <label> prepares a config under ~/.cyclops/hooks/ and prints wiring instructions (it refuses to touch vendor directories itself); the source installer can wire vendor hook files for you — merging around your existing handlers, backing the file up once, opt-out with CYCLOPS_NO_VENDOR_HOOKS=1. Either way, finish with cyclops hooks selftest <agent>, which sends one real no-op delivery and proves the ack fires. Ack ability is per-CLI: Claude, Codex, and Cursor can reach the verified tier; agy has no payload-matchable ack, so its deliveries honestly stay screen-tier.

The ledger is the debugger
Every one of these transitions became a line in the ledger, so when a delivery looks stuck you read the record, not the logs: find the last state line for the message id, then the gate lines above it — each carries a one-word cause. A hold always waits on an event, never a clock, so "stuck" always means "which event never arrived?". (The cause table is in the Contribute section below.)

Level 4 — Why it's built this way

Six decisions explain most of what looks unusual in this codebase. They're recorded in docs/development/HANDOFF.md with the alternatives that were rejected; here's the short form.

Ride tmux, don't replace it
Cyclops attaches to your existing tmux server through control mode (tmux -C) instead of hosting its own terminals. Comparable systems spend 7k–200k lines owning PTYs; Cyclops rejected that cost. The trade-off: every tmux quirk is Cyclops's problem, which is why all tmux code is confined to one crate and an advisory CI job builds tmux from master as an early-warning canary.
Manifests are data files
Everything Cyclops knows about a vendor CLI is one TOML file. Vendor behavior in Rust would mean a review-and-release cycle for every vendor UI tweak; in a manifest it's a text edit on the machine that has the problem. The schema has grown exactly twice, both times forced by a measurement (F19, F21) — a finding first, a schema change second.
The ledger is append-only NDJSON
One file per session, one JSON object per line, fsynced, never rewritten — corrections are new lines. A stranger with jq can read the full history months later without any Cyclops software. This is also why a daemon crash loses nothing: every fact was on disk before it was acted on. Measured, not guessed: no index needed, a 10,000-line scan takes ~7ms.
Zero polling
There are no interval timers anywhere. State arrives as tmux control-mode notifications and subscription pushes. Every timer in the codebase is a one-shot tied to an event that already happened (a debounce, a verify re-read, an ACK window — even the workspace's fade animations disarm themselves when the last one lands). The reasoning: a poll would hide a broken event path instead of surfacing it.
The pane title is a sensor, so Cyclops never writes it
Vendor CLIs put state information in the pane title, and manifests read it as evidence — Claude's spinner rules ARE the title tier. So Cyclops's own decoration (role and state) goes on the tmux pane border instead: writing the title would poison its own sensor and lose the race to any agent that publishes its own title anyway.
One trait, one implementation — on purpose
Delivery reaches a pane through an Injector seam (paste, submit, capture) with exactly one implementation, TmuxInjector. That seam is the designated escape lane to per-vendor headless protocols (Claude stream-json, Codex app-server JSON-RPC, Gemini ACP) if pasting into TUIs ever becomes untenable. It looks like over-abstraction; it's a recorded decision. Don't inline it.

Inside the workspace: Ctrl+B m names a pane, Ctrl+B s (or the chat button) messages an agent without leaving. Then wire hooks — receipts upgrade from screen-verified to agent-verified (fresh installs via the public installer can wire vendor hooks for you; CYCLOPS_NO_VENDOR_HOOKS=1 declines):

cyclops hooks install claude --agent reviewer
cyclops hooks selftest reviewer# proves they fire

A pane showing ? unknown means no manifest matched what's running there; cyclops status prints the exact fix. cyclops daemon status|log|stop manages the daemon.

Update your install

Pre-release v0.1.0-beta — updating is one verb. It says which build you're running, checks the source for a newer commit, reruns the installer from a fresh clone, refreshes any agent hooks it installed (they embed the binary's path), and prints the restart steps:

cyclops update# already-current stops right there
cyclops daemon stop# the running daemon is still the old binary
cyclops start# brings the new one up
cyclops --version# confirm
What updates never touch
Your config, workspaces, and the ledger under ~/.cyclops (your message history — nothing ever rewrites it). Manifests and themes you edited are never clobbered either; only unedited shipped copies are refreshed in place, recognized by hash, so fixes reach you without risking your changes.

The previous shell/Python implementation lives on at the read-only v1-final tag as historical predecessor reference.

Level 6 — Contribute

Everything below is what a reviewer will hold your first PR to. The short version: prove changes by running them (gates, fixtures, demos), never touch real tmux or a real home from a test, and treat docs as code — they are CI-verified against the binaries.

The loop — five gates, in this order

These are the same five core checks CI runs, so a green run here is a green run there:

cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo nextest run --workspace -E 'not package(cyclopsd)' --no-fail-fast# parallel-safe suites
cargo test -p cyclopsd --all-targets --no-fail-fast# daemon rigs preserve their process contract
cargo test --workspace --doc# nextest does not run doctests
python3 scripts/check-doc-paths.py# every quoted path must exist
./tests/e2e/parity-check.sh# docs must match binary output

Touching either installer adds cmp scripts/install.sh website/static/install.sh and ./tests/e2e/parity-check.sh --with-installer (a release build). CI also reruns the suite with scratch storage relocated, checks the website build, and runs an advisory job against tmux built from master.

Debug a stuck delivery — read the record
jq -c 'select(.id == "m-b90b2a")' ~/.cyclops/ledger/main.ndjson

Read the last state line first, then the gate lines above it. Each carries a one-word cause, and the cause tells you where to look — see the table below. Remember: a hold waits on an event, never a clock, so “stuck” is always the question “which event never arrived?”

House rules that bite newcomers

The long forms live in CONTRIBUTING.md and docs/development/INVARIANTS.md (eleven rules, each with the real-world damage it prevents). If you are touching delivery, the ledger, or anything that renders, read INVARIANTS first.

Tests never touch your tmux server or your real ~/.cyclops
Every test that needs tmux gets its own throwaway server through cyclops_testrig::TmuxServer (teardown is Drop, so it survives panics), and points CYCLOPS_HOME at scratch. Never invoke tmux directly in a test. Two guard tests enforce this because the rule was fixed three times and kept getting copied back in; shell and Python go through tests/e2e/lib/lib.sh.
Scratch paths come from cyclops_proto::scratch — never /tmp literals
Not /private/tmp (macOS-only), not std::env::temp_dir() (its long /var/folders path blows the ~104-byte Unix socket cap). This is finding F24 and it cost two milestones. CI runs the whole suite twice, once with CYCLOPS_TEST_TMP relocated, to catch a hardcoded path.
nextest needs --no-fail-fast, always
nextest must keep scheduling after a failure so one run reports every failing test. One portability bug passed green across two milestones because the visible failure count did not cover the full suite (F24). CI passes the flag; you should too.
Docs are CI-verified against the binaries
Never hand-write terminal output into a doc. parity-check.sh re-runs every command the README and docs quote and fails when a line drifts; the fix is to copy the new output from its transcript into the page in the same commit. check-doc-paths.py fails CI when a doc names a file that doesn't exist or a page no front door links to.
A behavior fix needs a test that fails before it
Write the test, watch it fail, then fix. A test written after the fix only proves the code passes its own test. And docs ship in the same commit as the behavior — a page describing something that no longer exists is a bug, not a stale doc.
No polling — find the event
If you are reaching for an interval timer, you have not found the event yet (INVARIANTS.md, rule 9). Every recompute rides a tmux notification, a socket request, or a one-shot deadline tied to something that already happened.
Wire changes are additive; vendor behavior goes in manifests
New protocol fields are optional, unknown fields are ignored in both directions, and a version mismatch warns rather than rejects. Anything Cyclops learns about a vendor CLI goes in a TOML manifest, never in Rust.
Record what you measured, and write plainly
A learned fact about tmux, a vendor CLI, or a platform goes in findings.md with the probe that proved it — comments cite these F-numbers. STYLE.md is binding on code, comments, and docs: write for a tired engineer who has never seen this repo.

Great first contributions

1. Teach Cyclops a new agent CLI one TOML file, no Rust

Adding an agent is the most common thing anyone does to this system, and it is deliberately code-free. Write one TOML file in resources/manifests/ (codex.toml is the closest thing to a template; the full page is docs/reference/MANIFESTS.md):

[agent] process_names
binds the file to a pane by its foreground command
add argv_basenames too if the CLI installs as a versioned symlink (F21)
[[rule]] blocks
read state off the pane title or the screen, by priority
titles are cheap; a title rule that decides skips capture entirely
[injection] verify_pattern
must contain <message_id>
that substitution proves the composer staged THIS message
[hooks] ack
declare it if the CLI can run hooks
declare nothing and the agent is tier-2 (screen receipts), which works

Prove it with fixtures, not by eye: put real screen captures in src/cyclops-manifest/tests/fixtures/ and register them in src/cyclops-manifest/tests/shipped_rules.rs. Then check it live with cyclops list, and pin it if binding is ambiguous: cyclops name %3 reviewer --manifest <id>. If you become convinced the schema itself must grow, that is a findings.md entry first and a schema change second — it has grown exactly twice, both times measurement-forced.

2. A small UI/UX change workspace · watch · theme

Good first surface: the full-screen workspace (cyclops-workspace), the live stream cyclops watch, or a theme under resources/themes/. Examples that stay reviewable: clearer empty states, denser or calmer spacing, a missing keybinding hint, a theme that fixes a contrast miss. Keep the change small enough that a reviewer can see the before/after in one sitting.

Guardrails: renderers use theme tokens, never raw colors; the pane title is a sensor — never write it; decoration goes on the pane border. If the change touches anything that prints (CLI tables, status lines, watch chrome that docs quote), read INVARIANTS.md first and expect parity-check.sh to notice drifted output.

3. Clarify the README or a public-facing guide prose, not invented output

Newcomers hit README.md and docs/guides/ first. Tightening a confusing paragraph, filling a missing “what do I do next”, or making QUICKSTART match how people actually set up a duo is high leverage — and docs are treated as code here.

Guardrails: never hand-write a quoted terminal block; if output changed, copy it from the parity-check.sh transcript in the same commit. Every path a doc names must exist (check-doc-paths.py), and every page must be reachable from README.md or HANDOFF.md. The landing site under website/ is a separate job — only touch it on an explicit request, and keep website/static/install.sh byte-identical to scripts/install.sh.
